2. C8 IDEMPOTENCY — PROOF
=======================================================================

2.1 THE EXACT RACE CONDITION

Scenario: Two concurrent requests to checkout the same Booking.

```
Timeline:
T1: Request A reads Booking.orderId = NULL
T2: Request B reads Booking.orderId = NULL
T3: Request A creates Order A (T1 transaction)
T4: Request A attempts conditional UPDATE Booking SET orderId = A WHERE id = X AND orderId IS NULL
T5: Request B creates Order B (T1 transaction)
T6: Request B attempts conditional UPDATE Booking SET orderId = B WHERE id = X AND orderId IS NULL
```

2.2 EXACT TRANSACTION FLOW (Single $transaction)

```typescript
async checkoutBooking(bookingId: string, userId: string, dto: CheckoutDto) {
  return this.prisma.$transaction(async (tx) => {
    // 1. Validate Booking exists, tenant matches, status valid
    const booking = await tx.booking.findUnique({ where: { id: bookingId } });
    if (!booking) throw new NotFoundException('Booking not found');
    if (booking.tenantId !== tenantId) throw new NotFoundException('Booking not found');
    if (!['BOOKED','CONFIRMED','ACTIVE'].includes(booking.status)) {
      throw new ConflictException('Booking cannot be linked in current status');
    }
    if (booking.orderId) {
      // Idempotent: already linked
      const existingOrder = await tx.order.findUnique({ where: { id: booking.orderId } });
      return { order: this.toOrderSummary(existingOrder), booking: this.toBookingSummary(booking) };
    }

    // 2. Create Order via existing T1 (adapted for tx)
    const order = await this.createOrderInTx(tx, userId, {
      items: checkoutItems,
      customerId: dto.customerId,
    });

    // 3. CONDITIONAL LINK — THE CRITICAL STEP
    const updated = await tx.booking.update({
      where: { id: bookingId, orderId: null },  // CONDITIONAL: only if unlinked
      data: { orderId: order.id },
    });

    if (!updated) {
      // Race lost — another request won
      const existingOrder = await tx.order.findUnique({ where: { id: booking.orderId } });
      return { order: this.toOrderSummary(existingOrder), booking: this.toBookingSummary(booking) };
    }

    return { order: this.toOrderSummary(order), booking: this.toBookingSummary(updated) };
  });
}
```

2.3 EXACT RACE RESOLUTION

```
Timeline with conditional UPDATE:

T1: Request A reads Booking.orderId = NULL
T2: Request B reads Booking.orderId = NULL
T3: Request A creates Order A (T1 in same tx)
T4: Request A UPDATE Booking SET orderId=A WHERE id=X AND orderId IS NULL → 1 row affected
T5: Request B creates Order B (T1 in same tx)
T6: Request B UPDATE Booking SET orderId=B WHERE id=X AND orderId IS NULL → 0 rows affected
T7: Request B detects 0 rows → reads Booking → finds orderId=A
T8: Request B returns existing Order A (200)
T9: Request A returns Order A (200)
```

RESULT: Exactly ONE Order linked. Deterministic. No orphans.

2.4 TRANSACTION BOUNDARY PROOF

The checkout operation executes in ONE Prisma $transaction:

```typescript
return this.prisma.$transaction(async (tx) => {
  // 1. Validate Booking (read)
  const booking = await tx.booking.findUnique({ where: { id: bookingId } });
  
  // 2. Create Order (T1) — reuses existing OrderService logic
  const order = await this.createOrderInTx(tx, userId, checkoutData);
  
  // 3. CONDITIONAL LINK — THE CRITICAL STEP
  const updated = await tx.booking.update({
    where: { id: bookingId, orderId: null },  // CONDITIONAL!
    data: { orderId: order.id },
  });
  
  if (!updated) {
    // Lost race — re-read and return winner's Order
    const existing = await tx.order.findUnique({ where: { id: booking.orderId } });
    return { order: this.toOrderSummary(existing), ... };
  }
  
  return { order: this.toOrderSummary(order), booking: this.toBookingSummary(updated) };
});
```

WHY THIS WORKS:
- Prisma $transaction = single PostgreSQL transaction
- Conditional UPDATE is atomic (single statement)
- If UPDATE affects 0 rows → race lost → re-read winner
- If Order creation fails → entire transaction rolls back → Booking unlinked
- If link UPDATE fails → entire transaction rolls back → Order rolled back

2.5 FAILURE MODES

| Scenario | Outcome |
|----------|---------|
| Order creation fails (stock, validation) | Transaction rolls back → Booking unlinked, no Order |
| Link UPDATE affects 0 rows (race lost) | Re-read Booking → return winner's Order (200) |
| Link UPDATE fails (FK violation) | Transaction rolls back → Order rolled back |
| Client loses response after commit, retries | Reads Booking.orderId → returns existing Order (200) |
| Network timeout before commit | No commit → rollback → safe retry |

2.6 ORPHAN ORDER PREVENTION

Question: Can an orphan Order survive (Order created but Booking unlinked)?

ANSWER: NO, not durably.

- If link UPDATE fails → transaction rolls back → Order deleted
- If transaction commits → link exists
- If process crashes after commit → both committed (durable)
- If crash before commit → rollback → neither exists

Orphan Order could only exist transiently during transaction, never committed.

```typescript
function scopeArgs(operation: string, args: unknown, tenantId: string): void {
  switch (operation) {
    case 'create':
      args.data = { ...args.data, tenantId };
      break;
    case 'update':
    case 'updateMany':
      args.where = { ...args.where, tenantId };
      args.data = { ...args.data, tenantId };
      break;
    // ...
  }
}
```

4.3 TENANT INVARIANT PROOF

| Layer | Mechanism |
|-------|-----------|
| Application | TenantContext.requireTenantId() fails closed |
| Prisma Extension | Injects tenantId into every create/update/find |
| Database FK | FK references enforce same tenant (tenantId on both tables) |
| Cross-tenant query | Extension injects tenantId → foreign row resolves to null → 404 |

PROOF: Cross-tenant link impossible
- Booking in Tenant A, Order in Tenant B
- Booking.orderId = Order.id (Tenant B)
- Prisma extension injects Tenant A's tenantId into Booking UPDATE
- FK check: Order.tenantId (Tenant B) ≠ Booking.tenantId (Tenant A)
- PostgreSQL FK violation → P2003 → 409 Conflict

Both application-layer validation AND database constraint enforce tenant invariant.
