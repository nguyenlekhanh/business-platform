3. THE EXACT SERVICE MODEL
-----------------------------------------------------------------------
prisma/schema.prisma (all additive):
  enum ServiceStatus { DRAFT  ACTIVE  ARCHIVED }   // the ProductStatus
                                                   // catalog convention
  model Service {
    id          String        @id @default(cuid())
    tenantId    String                    // server-derived (F5)
    name        String                    // unique within the tenant
    description String?
    status      ServiceStatus @default(DRAFT)
    createdAt / updatedAt
    tenant Tenant @relation(..., onDelete: Cascade)
    @@unique([tenantId, name])
    @@index([tenantId])
    @@index([tenantId, createdAt, id])   // keyset parity
  }
  Field semantics:
  - name: the service's display name; unique per tenant (composite
    constraint — same name allowed in different tenants, no
    cross-tenant existence leak).
  - description: optional free-text (MaxLength 2000, the Category/
    Product convention).
  - status: DRAFT default on create; PATCH carries the archive flow;
    ARCHIVED = soft retirement (the established catalog convention —
    "do not implement lifecycle behavior beyond the established
    pattern").
  Case sensitivity: the repository's established uniqueness is exact
  case-sensitive composite text (Category/Product) — no case-insensitive
  collation was invented.

-----------------------------------------------------------------------
4. TENANT ISOLATION
-----------------------------------------------------------------------
Service is registered in TENANT_SCOPED_MODELS (src/common/database/
prisma/tenant-scoping.extension.ts) — every top-level read/write is
extension-scoped and fails closed without a TenantContext. tenantId is
server-derived only (requireTenantId at every service method; the
extension injects it into create/update so a client can never override
it). No DTO accepts tenantId (whitelist 400 — integration-proven on
create, update, AND query). Cross-tenant access returns the uniform
404 (no existence oracle) — proven both directions on GET and PATCH,
plus the ambient-context direct-Prisma scoping test. No raw SQL.

5. UNIQUENESS + CONCURRENCY
-----------------------------------------------------------------------
  - @@unique([tenantId, name]) + the handwritten UNIQUE INDEX in the

  - No application read-then-create check exists anywhere in the

  - Concurrency integration test: two concurrent POSTs with the same

  - Rename collisions hit the same constraint (409).

7. API SURFACE
-----------------------------------------------------------------------
GET   /services            service:read     200 { data, meta.nextCursor }
GET   /services/:id        service:read     200 ServiceSummary | 404
POST  /services             create|manage   201 ServiceSummary | 409
PATCH /services/:id        service:manage   200 ServiceSummary | 404|409
  - PATCH (not PUT) — the Phase 3+ convention on new domains (D2),
    verified against the actual controllers.
  - Guard chain: JWT (global) -> TenantResolutionGuard -> PermissionsGuard;
    TenantContextInterceptor; whitelist+transform+forbidNonWhitelisted.
  - NO DELETE route: the approved scope has no deletion semantics; the
    omission is deliberate and REPORTED (soft retirement via PATCH
    status=ARCHIVED is the established convention; a future Booking FK
    will RESTRICT deletion the way Product's does for Category).
  - No booking/availability/schedule/staff/resource/pricing endpoints.

-----------------------------------------------------------------------
8. DTO SECURITY
-----------------------------------------------------------------------
CreateServiceDto: name (@IsString @IsNotEmpty @MaxLength(200)); optional
description (@MaxLength(2000)); optional status (@IsEnum(ServiceStatus)).
UpdateServiceDto: all-optional (empty patch = no-op). ServiceListQueryDto
extends PageQueryDto + optional status filter (the ProductListQueryDto
shape). NO tenantId/id/createdAt/updatedAt anywhere; the whitelist+
forbidNonWhitelisted rejects all of them (400) AND the deferred-domain
fields (price, amountMinor, currency, durationMinutes, staffId,
resourceId, bookingId, scheduleId) — integration-proven with zero rows
created / unchanged rows after rejected patches.

-----------------------------------------------------------------------
9. RBAC
-----------------------------------------------------------------------
Three new keys follow the exact catalog conventions (B21):
  service:read   -> GET routes
  service:create -> POST (RequireAnyPermission(create, manage))
  service:manage -> PATCH (RequireAnyPermission(manage))
Role defaults: admin += all three; employee += service:read only; owner
keeps semantic all-permissions. Verified behaviors: unauthenticated ->
401; missing key -> 403 per action; manage-only can create+patch but
gets 403 on reads; create-only can create but cannot read/patch (i.e.,
create does NOT imply manage — the relationship is exactly the guard
metadata, nothing implicit); owner works without grants.
