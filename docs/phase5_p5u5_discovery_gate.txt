2. EXISTING ORDER CONTRACT (PHASE 3 U6)
=======================================================================
REPOSITORY FACT:
- Order model: id, tenantId, userId (creator), customerId?, status
  (PENDING|PAID|CANCELLED), currency (Char(3)), subtotalMinor (BigInt),
  cancelledAt?, timestamps.
- State machine: PENDING → PAID (via payment capture tx) |
  PENDING → CANCELLED (POST /orders/:id/cancel, restocks).
  PAID is terminal in Phase 3; cancelling PAID → 409.
- Status is NEVER client-writable (whitelist rejects status field).
- OrderItem: immutable snapshots at creation — productName, variantName,
  sku, quantity, currency, unitAmountMinor, lineTotalMinor.
  FK to ProductVariant RESTRICT (history survives variant deletion).
- Order N-1 Customer (nullable FK RESTRICT — P2003 → 409 if orders exist).
- Order N-1 User (creator).
- T1 (create): variants ACTIVE + uniform-currency prices + guarded
  stock decrement + create Order + OrderItems + cart CONVERTED.
  All-or-nothing via interactive transaction.
- T3 (cancel): guarded PENDING→CANCELLED + restock increments.
- Cross-module access via services; order-service touches other
  models inside its transaction (atomicity) — documented per-call.

3. EXISTING PAYMENT CONTRACT (PHASE 3 U7)
=======================================================================
REPOSITORY FACT:
- Payment model: id, tenantId, orderId, status
  (PROCESSING|CAPTURED|FAILED), method (free-form string, e.g. CASH/CARD),
  amountMinor (BigInt), currency (Char(3)), timestamps.
- State machine: PROCESSING → CAPTURED (T2: also flips Order PENDING→PAID
  atomically) | PROCESSING → FAILED (Order stays PENDING).
  CAPTURED/FAILED are terminal and immutable.
- Idempotency: re-capture of CAPTURED returns 200 no-op; FAILED cannot
  capture (409); CAPTURED cannot fail (409).
- T5 create: only for PENDING Order with no existing CAPTURED payment.
  Multiple PROCESSING payments allowed (documented rule).
- T2 capture: guarded updateMany PROCESSING→CAPTURED + Order PENDING→PAID
  (count==1 both, rollback on 0). T2 fail: Order untouched.
- Simulated gateway only (approved D4): capture/fail are permission-guarded
  staff actions; no external providers, webhooks, refunds.
- Idempotent terminal replays proven; concurrent capture/fail races
  arbitrated by guarded updates.

4. EXISTING INVENTORY CONTRACT (PHASE 3 U4, P4-U3)
=======================================================================
REPOSITORY FACT:

- Partial unique indexes: (variantId) WHERE storeId IS NULL (global

7. CROSS-DOMAIN INTEGRATION OPTIONS
=======================================================================

INFERENCE: The repository provides TWO proven templates for cross-domain
links:
1. PosSale pattern (P4-U2): additive provenance link (Order→PosSale)
   without touching Order/Payment state machines. PosSale captures
   device/session/store/cashier provenance; Order/Payment state machines
   remain untouched.
2. Customer→Order pattern (Phase 3 D1): nullable FK + RESTRICT + P2003
   → 409. Customer is tenant-wide, shared across stores.

INFERENCE: For Booking↔Commerce, the repository supports these
architectural primitives:
- Additive FK with RESTRICT (Customer→Order, PosSale→Order)
- Provenance table for cross-domain provenance (PosSale)
- Order/Payment state machines are FROZEN and must not be modified
- No refunds exist anywhere (Phase 3 §7, Phase 4: no refunds)

=======================================================================
8. CROSS-DOMAIN INTEGRATION OPTIONS
=======================================================================

OPTION A — NO COMMERCE LINK (Minimal)
-------------------------------------
Booking remains purely temporal (Service + time). No Order, no Payment,
no pricing. Commerce integration = zero.
- Pros: Minimal, keeps domains separated, zero new decisions.
- Cons: No monetization path; Booking is purely temporal reservation.

OPTION B — ADDITIVE PROVENANCE LINK (PosSale Pattern)
-----------------------------------------------------
Booking creates/references an Order via additive provenance table
(like PosSale). Booking remains temporal; Order handles commerce.
- Pros: Reuses proven additive pattern; Order/Payment state machines
  untouched; Payment timing/refunds decided at Order level.
- Cons: Requires new provenance table; Booking→Order link optional
  (nullable FK); does not answer "who pays when".

OPTION C — BOOKING CREATES ORDER (Synchronous)
----------------------------------------------
Booking creation directly creates Order (+ Payment) in same
transaction. Booking holds optional orderId (FK).
- Pros: Direct monetization; atomic creation.
- Cons: Couples temporal domain to financial domain; Order/Payment
  logic invoked from Booking service; retry/failure semantics complex;
  does a Booking *require* payment?

OPTION D — ORDER REFERENCES BOOKING (Reverse)
---------------------------------------------
Order optionally references a Booking (like PosSale). Booking is
created first; Order created later (checkout, POS, etc.) and
optionally links to Booking.
- Pros: Booking remains pure temporal; Order is the commerce root;
  multiple Bookings could theoretically link to one Order (1:N?).
- Cons: Booking must exist before Order; who creates Booking?

=======================================================================
9. RECOMMENDED MINIMAL OPTION
=======================================================================

REPOSITORY FACT: The PosSale pattern is the ONLY existing cross-domain
link in the repository. It is additive, non-invasive, and preserves
Order/Payment state machines.

RECOMMENDATION: Option B — Additive Provenance Link (Booking→Order
via new BookingSale/BookingProvenance table).
- Booking remains temporal/catalog domain (no money, no payment).
- Optional link to Order created when customer pays.
- Order/Payment state machines untouched (FROZEN).
- Payment timing/refunds decided at Order level (not Booking).
- Cross-store customer already allowed (P5-U2 B14 sub-option i).

ARCHITECTURAL RECOMMENDATION: The MINIMUM required cross-domain
relationship is an OPTIONAL, ADDITIVE provenance link from Booking
to Order. This requires NO new decisions about pricing, payment
timing, refunds, or inventory — those remain at Order level.

11. TRANSACTION BOUNDARIES
=======================================================================

REPOSITORY FACT: Existing transaction patterns (all interactive,
tenant-scoped, top-level writes only, no nested relation writes):

T1 (Order create): validate variants ACTIVE + uniform-currency prices
  + guarded stock decrement + create Order + OrderItems + cart CONVERTED.
  All-or-nothing via interactive transaction.

T2 (Payment capture): guarded PROCESSING→CAPTURED + Order PENDING→PAID
  (count==1 both, rollback on 0). Idempotent terminal replays.

T3 (Order cancel): guarded PENDING→CANCELLED + restock increments.

T5 (Payment create): Order PENDING + no CAPTURED payment (multiple
PROCESSING allowed).

PosSale (P4-U2): thin orchestration over T1+T5+T2.

INFERENCE: For Booking↔Order linkage, the MINIMAL atomic boundary is:
- Booking creation is independent (no Order).
- Order creation (if triggered by Booking) uses existing T1 transaction
  — Booking just provides the serviceId/customerId/startAt/endAt as
  input to T1.
- NO new transaction boundary spanning Booking + Order + Payment
  unless explicitly approved.

PROPOSED DECISION: The Booking→Order link is created OUTSIDE the
Booking transaction. Booking is created first (its own transaction).
Order creation happens later (checkout, POS, webhook) using existing
T1. The Booking→Order link is additive (nullable FK or provenance
table), created when Order is created.

=======================================================================
12. IDEMPOTENCY / CONCURRENCY
=======================================================================

REPOSITORY FACT: Two proven patterns exist:
1. EXCLUDE constraint (Reservation, Booking) — DB-authoritative
   overlap arbitration. Zero application logic.
2. Guarded updateMany + client idempotency key (PosOperation) —
   deduplication at sync/retry.

INFERENCE: For Booking→Order linkage, idempotency must be defined:
- If Order created from Booking: need natural key (BookingId?) or
  client idempotency key to prevent duplicate Order creation on retry.
- If multiple payments per Booking: T5 already allows multiple
  PROCESSING payments; only one CAPTURED allowed.

PROPOSED DECISION: No new idempotency mechanism in P5-U5. Reuse
existing patterns: Booking natural key (serviceId + startAt?) for
Booking creation; Order T5 rules for Payment; client-generated
idempotency key only if Booking→Order is synchronous.

=======================================================================
13. FAILURE / COMPENSATION SEMANTICS
=======================================================================

REPOSITORY FACT: Existing compensation patterns:
- Order cancel → restock (exactly once, guarded).
- Payment capture fail → rollback (no partial CAPTURED/CANCELLED).
- Payment fail → Order stays PENDING, no stock change.
- PosSale sync reject → intent stays PENDING/REJECTED, zero mutation.
- NO refunds anywhere (Phase 3, Phase 4).

INFERENCE: If Booking cancellation triggers Order cancellation, it
must use existing T3 (guarded CANCEL + restock). No new refund
mechanism unless explicitly approved (B19: no refunds unless
explicitly approved).

RECOMMENDATION: Booking cancellation = status change only (CANCELLED).
Order cancellation (if linked) uses existing T3. No refund logic
in P5-U5 unless B19 explicitly approved.
