2. PROPOSED ARCHITECTURE
-----------------------------------------------------------------------
MODULE: src/pos/ (new NestJS module, one aggregate root family per
the Phase 3 convention; PosDevice + PosSession are one bounded
foundation context — like Cart+CartItem were one U5 unit).

Two aggregate roots:

  PosDevice — the registered terminal.
    - Created by tenant staff (with RBAC) for a specific same-tenant
      Store; server generates the credential secret.
    - Status lifecycle: ACTIVE -> SUSPENDED (revoke) -> RETIRED
      (terminal). Guarded transitions, no client-writable status.
    - Credential: server-issued random material (crypto.randomBytes
      pattern, like RefreshToken), stored ONLY as sha256 hex
      (credentialHash @unique), returned in plaintext EXACTLY ONCE
      in the registration response; re-issuance = rotate credential.
    - Never trusts device-asserted tenant/store: tenant comes from
      context; storeId resolved via tenant-scoped Store lookup
      (foreign/unknown store -> 404, the Asset.storeId precedent).

  PosSession — the cashier shift on a device.
    - Opened by an authenticated member User (cashier) on an ACTIVE
      device; inherits the device's store; records openedBy userId.
    - Lifecycle: OPEN -> CLOSED (guarded transition, closedAt set).
      Only ONE OPEN session per device at a time (service-side guard
      + tested; a small create race is prevented by a partial unique
      index in the migration — see §5 — closing the U5 cart race
      pattern's known tolerance).
    - Authorization: opening/closing requires the pos:* permission
      (A1); the opener is recorded; future sale intents (P4-U4+)
      anchor to sessionId. Sessions are NOT cross-device.
    - closedAt/finalized data: minimal per D9 (A3 pending).

Both models registered in TENANT_SCOPED_MODELS (fail-closed
centralized scoping; server-derived tenantId only; uniform cross-
tenant 404; no raw SQL).

Phase 3 reuse map (no modifications to frozen code):
  - Credential hashing  <- RefreshToken sha256 pattern (auth).
  - Store resolution    <- Asset.storeId app-side pattern (asset).
  - Guard chain/pipes   <- identical to PaymentController (U7 CP6).
  - Status machines     <- Order/Payment guarded-transition style.
  - Migration style     <- additive handwritten SQL, deploy-only.

3. PROPOSED SCHEMA (PLANNING ONLY — schema.prisma UNTOUCHED)
-----------------------------------------------------------------------
enum PosDeviceStatus { ACTIVE  SUSPENDED  RETIRED }
enum PosSessionStatus { OPEN    CLOSED }

model PosDevice {
  id             String   @id @default(cuid())
  tenantId       String
  storeId        String            // same-tenant Store (app-side
                                   // resolved like Asset.storeId)
  name           String            // human label, unique per tenant
  status         PosDeviceStatus @default(ACTIVE)
  credentialHash String   @unique // sha256 hex of server-issued secret
  lastSeenAt     DateTime?        // updated at sync (later units)

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  tenant  Tenant  @relation(..., onDelete: Cascade)
  store   Store   @relation(..., onDelete: Restrict) // blocks store
                                                   // delete w/ devices
  sessions PosSession[]

  @@unique([tenantId, name])
  @@index([tenantId])
  @@index([tenantId, createdAt, id])   // keyset parity
  @@index([storeId])
}

model PosSession {
  id        String   @id @default(cuid())
  tenantId  String
  deviceId  String
  storeId   String            // denormalized from device for reporting
                               // + tenant-scoped queries
  userId    String            // cashier (opener)
  status    PosSessionStatus @default(OPEN)
  openedAt  DateTime @default(now())
  closedAt  DateTime?

  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt

  tenant Tenant   @relation(..., onDelete: Cascade)
  device PosDevice @relation(..., onDelete: Cascade) // sessions die
                                                     // with device
  store  Store    @relation(..., onDelete: Restrict)
  user   User     @relation(..., onDelete: Cascade)  // cashier rows

  @@index([tenantId])
  @@index([tenantId, createdAt, id])
  @@index([deviceId, status])
  @@index([userId])
}

DATABASE CONSTRAINTS (handwritten SQL only, Prisma DSL cannot express):
  - CHECK openedAt <= closedAt (when closedAt not null).
  - Partial unique index enforcing ONE OPEN session per device:
      CREATE UNIQUE INDEX PosSession_one_open_per_device
      ON PosSession(deviceId) WHERE status = 'OPEN';
    (This deliberately closes the race tolerance the U5 cart
     documented — a device is single-cashier-at-a-time by nature.)

LIFECYCLE / DELETION:
  - PosDevice: NO hard-delete endpoint (financial-history-adjacent
    identity + future sync audit anchor); RETIRED is the terminal
    soft state — mirrors Order/Payment no-delete precedent. (A6.)
  - PosSession: NO delete (shift history). CASCADE via device only
    (device rows are never deleted via API, so this is belt+braces).
  - Store delete RESTRICT while devices/sessions reference it.

CONCURRENCY:
  - Session open: partial unique index arbitrates races (409
    mapping on P2002-style violation; message 'Device already has an
    open session').
  - Status transitions: guarded updateMany WHERE status=<expected>
    with count==1 (Payment T2 pattern).

MIGRATION (PLANNING — not created):
  - ONE additive migration: 20260821120000_add_pos_foundation.
    Creates the two enums, two tables, indexes/FKs/CHECKs/partial

4. API SURFACE (PROPOSED — mirrors §11 Phase 3 conventions)
-----------------------------------------------------------------------
All routes under the standard guard chain
JwtAuthGuard -> TenantResolutionGuard -> PermissionsGuard +
TenantContextInterceptor + whitelist/transform/forbidNonWhitelisted
ValidationPipe (PaymentController pattern).

  POST   /pos/devices            pos:create (A1)
         { storeId, name } -> 201 DeviceRegistrationSummary
         { ..., credential: "<plaintext-secret>" }   // ONE-TIME
         (credential NEVER appears again in any response)
  GET    /pos/devices             pos:read
         keyset-paginated list (shared pagination module) with
         status filter (parity with /orders).
  GET    /pos/devices/:id         pos:read -> DeviceSummary
         (NEVER includes credentialHash or credential).
  PATCH  /pos/devices/:id         pos:manage
         { name? } only — status changes go through the lifecycle
         endpoints below (status not client-writable via PATCH).
  POST   /pos/devices/:id/suspend   pos:manage  ACTIVE->SUSPENDED
  POST   /pos/devices/:id/resume    pos:manage  SUSPENDED->ACTIVE
  POST   /pos/devices/:id/retire    pos:manage  *->RETIRED (terminal)
     All transitions guarded + @HttpCode(200); invalid source states
     -> 409 (Order-cancel message pattern). RETIRED is terminal.
  POST   /pos/devices/:id/rotate-credential  pos:manage
     -> 200 { credential } (new one-time secret; old hash replaced;
     D6 revocation/rotation).

  POST   /pos/sessions            pos:manage (cashier opens shift; A1)
         { deviceId } -> 201 SessionSummary
         (server derives store + cashier userId from context; device
         must be ACTIVE; one-open-session enforced).
  GET    /pos/sessions/:id        pos:read -> SessionSummary
  POST   /pos/sessions/:id/close  pos:manage  OPEN->CLOSED
         guarded + @HttpCode(200); closing an already-CLOSED session
         -> 409.

DTO whitelist rejections (400): tenantId, storeId injection on
session create (store comes from the DEVICE, never the client),
deviceId/status/id/timestamps injection, unknown fields — all
integration-tested (Phase 3 matrix).

ERRORS (uniform 404 policy): unknown/foreign device or session id
-> 'Pos device not found' / 'POS session not found'; foreign storeId
-> 'Store not found' (Asset.storeId precedent); suspended/retired
device session-open -> 409 'Device is not active'.

5. SECURITY MODEL (P4-U1)
-----------------------------------------------------------------------
  - Tenant: server-derived via AsyncLocalStorage (unchanged); both
    models tenant-scoped; cross-tenant reads/writes -> uniform 404.
  - Device identity: server-issued only (D6); credentialHash never
    exposed in ANY response or log (RefreshToken precedent); the
    plaintext secret exists only in the registration/rotation
    response. Rotation invalidates the old secret atomically.
  - Revocation: SUSPENDED/RETIRED devices refuse future
    session-opens (409) — the documented authorization failure for
    device-level revocation. (Sync-time enforcement lands in P4-U5
    and re-checks status on every request, per D6/D7.)
  - RBAC: additive pos:* keys only; existing catalog untouched;
    owner semantic-all unchanged; admin/employee defaults per A1.
  - Session ownership: sessions belong to (device, cashier);
    closing requires pos:manage (A1); no user-level isolation is
    proposed for session READS within the tenant (tenant-scoped
    reads, the Order precedent) — pending A1 confirmation.
  - Input: every DTO whitelisted; status never client-writable.
  - No raw SQL; no nested relation writes; top-level ops only.

  - RBAC matrix: no-permission 403 per key; manage-only vs read-only

  - Lifecycle: register -> suspend -> resume -> retire terminal
    (full matrix incl. invalid source states -> 409); retired
    device cannot open a session.
  - Credential security: registration response contains the secret
    exactly once; NO row (or any later GET) contains/equals the raw
    material; the stored hash equals sha256(secret); rotation
    invalidates (old hash gone, new hash present, secret returned
    once).
  - Session lifecycle: open/close happy path; two concurrent opens
    on one device -> exactly one 201 + one 409 (deterministic
    concurrency, U4 inventory-race pattern); close is guarded and
    idempotent-rejected (409); CHECK openedAt<=closedAt respected.
  - Store interaction: store with devices cannot be deleted (409,
    the Category/Product P2003 precedent).

        pos:read | pos:create (register device) | pos:manage
        (suspend/resume/retire/rotate, sessions open/close)
      admin += pos:manage; employee += pos:manage (cashiers are

      ALTERNATIVE: pos:register key for registration only); owner

  A2. Credential transport format for sync (P4-U5): PROPOSAL header
        'X-POS-Device-Credential: <secret>' alongside the cashier
        Bearer JWT; constant-time hash comparison (argon2 not needed
        for 384-bit random material — RefreshToken precedent).
  A3. Session close payload: bare close (PROPOSAL) vs financial
      summary (opening/closing cash counts) — the latter adds money
      fields; recommend deferring summary to P4-U7.
  A4. Who registers devices: pos:manage (admin-style, PROPOSAL) vs a
      dedicated pos:register key.
  A5. Store binding: fixed at registration (PROPOSAL — sessions
      inherit; moving a device = retire + re-register) vs PATCHable
      storeId. PROPOSAL preserves audit clarity.
  A6. Device deletion: no hard delete, RETIRED terminal (PROPOSAL,
      Order/Payment precedent). Confirm.
