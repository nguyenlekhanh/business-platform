3. IMPLEMENTATION FINDINGS (CODE AUDIT)
-----------------------------------------------------------------------
PAYMENT STATE MACHINE — VERIFIED
  - PROCESSING -> CAPTURED (capturePayment) and PROCESSING -> FAILED
    (failPayment) are the only transitions; status is never
    client-writable.
  - Terminal-state protection: CAPTURED payment re-capture is
    idempotent-success (returns existing row, no writes); FAILED payment
    capture -> 409 "Failed payment cannot be captured"; CAPTURED payment
    fail -> 409 "Captured payment cannot be failed"; FAILED re-fail is
    idempotent-success.
  - Order coupling: capture flips Order PENDING -> PAID inside the same
    transaction; fail never touches the Order (stays PENDING).

TRANSACTION INTEGRITY (T2/T5) — VERIFIED
  - T2 capture runs inside prisma.$transaction: guarded
    Payment.updateMany({ id, status: PROCESSING } -> CAPTURED) with
    count==1 enforcement, THEN guarded Order.updateMany({ id,
    status: PENDING } -> PAID) with count==1 enforcement. Either count==0
    throws, rolling back BOTH writes (integration test proves the
    Payment stays PROCESSING when the Order guard fails — no partial
    CAPTURED/CANCELLED state).
  - T2 fail is a single guarded updateMany; the Order is never written.
  - T5 createPayment validates Order PENDING and no existing CAPTURED
    payment before inserting the PROCESSING row; multiple PROCESSING
    payments for one Order remain allowed (documented business rule).
  - Concurrency: two racing captures (or capture-vs-fail) are arbitrated
    by the guarded updateMany — exactly one winner; integration tests
    verify only 200/409 outcomes and consistent final DB state.

MONEY INVARIANTS — VERIFIED
  - Payment.amountMinor is copied server-side from Order.subtotalMinor
    and Payment.currency from Order.currency (payment.service.ts:62-63);
    the client supplies only orderId + method.
  - PaymentSummary.amountMinor uses BigInt.toString() — string at the
    API boundary in every response; DB column stays exact BIGINT.

API / DTO SURFACE — VERIFIED
  - Exactly the four §11 endpoints: POST /payments (payment:create),
    GET /payments/:id (payment:read), POST /payments/:id/capture
    (payment:manage, @HttpCode(200)), POST /payments/:id/fail
    (payment:manage, @HttpCode(200)). No listing/pagination/refunds/
    webhooks/gateways/new states.
  - CreatePaymentDto exposes only orderId (@IsString @IsNotEmpty) and
    method (@IsString @IsNotEmpty @MaxLength(50)); controller-level
    ValidationPipe (whitelist + transform + forbidNonWhitelisted)
    rejects tenantId/amountMinor/currency/status/id/timestamps/unknown
    fields with 400 (integration-tested in CP7).

4. SECURITY FINDINGS
-----------------------------------------------------------------------
  - 'Payment' is registered in TENANT_SCOPED_MODELS
    (tenant-scoping.extension.ts:28): every top-level Payment read/write
    is force-scoped to the AsyncLocalStorage tenant context and fails
    closed without context.
  - tenantId is never accepted from the client (DTO whitelist rejects
    it; the create path derives tenantId from the resolved Order row).
  - Cross-tenant Payment/Order references resolve to the uniform 404
    "Payment not found" / "Order not found" (no existence oracle); CP7
    integration tests prove cross-tenant capture/fail attempts leave
    the owning tenant's rows untouched.
  - No raw SQL ($queryRaw/$executeRaw) anywhere in src/payment.
  - Guard chain on all four routes: JwtAuthGuard -> TenantResolutionGuard
    -> PermissionsGuard + TenantContextInterceptor.
  - RBAC verified in the catalog AND by behavior: payment:read/create/
    manage defined; admin += PAYMENT_MANAGE; employee += PAYMENT_CREATE;
    owner semantic-all; manage-only role can capture but cannot read or
    create; employee can create orders+payments but cannot read/capture/
    fail payments.
