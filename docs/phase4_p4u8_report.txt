-----------------------------------------------------------------------

chain: a device is PERMANENTLY bound to ONE store (A5, P4-U1); every
PosOperation's storeId is derived from its session's device and frozen;
sync validates stock ONLY against operation.storeId (pos-sync.service.ts:
317-322) and T1 decrements only that pool (P4-U3 inventoryScope). The
repository's domain model does NOT require device-to-device store
isolation WITHIN a tenant (tenant-level staff legitimately read all
devices' reports — the same tenant-scoped-read convention as Order).
No ambiguity, no STOP: store isolation is exactly "one pool per
(device->store), operations never cross pools," which is verified.

3. THE CONSOLIDATED VERIFICATION SUITE (the only deliverable)
-----------------------------------------------------------------------
NEW src/pos/p4u8-cross-domain.integration.spec.ts (9 tests, real
AppModule + supertest + real PostgreSQL, tenant A/B fixtures):
 1. TWO DEVICES OFFLINE simultaneously, independent store pools: both
    sync ACCEPTED; each pool drains independently to 0; a third intent
    on the drained pool -> deterministic OUT_OF_STOCK with the OTHER
    store's pool untouched (cross-pool no-leak).
 2. TRUE cross-device last-unit race on the SAME store pool (two
    devices, two sessions, 2 units): concurrent sync -> exactly
    [ACCEPTED, OUT_OF_STOCK]; exactly ONE Order and ONE Payment across
    the whole tenant; the loser's later retry stays rejected.
 3. CREDENTIAL MATRIX: device A's credential CANNOT sync device B's
    operation (401, zero execution, then the right credential still
    succeeds); a SUSPENDED device at sync -> 409.
 4. CROSS-TENANT FULL-SURFACE REPLAY: every tenant-A identifier — the
    accepted op, rejected op, device, session, operation LIST route,
    device RECONCILIATION route, session RECONCILIATION route, Order
    id, Payment id, store-scoped inventory, device, session — replayed
    against a fully-POS+cross-domain-permissioned tenant-B admin ->
    UNIFORM 404 on all 10 probes; tenant A unchanged (status still
    ACCEPTED, stock unchanged); tenant B has zero orders. Feed-cursor
    replay: tenant A's cursor against tenant B returns ONLY B's rows
    (isolated per-tenant watermark spaces), and vice versa.
 5. CROSS-SESSION: an op retains its original session after the shift
    closes (frozen), a NEW session on the same device never rebinds it,
    the PosSale provenance records the ORIGINAL session, and the new
    session's reconciliation report is empty while the old one holds
    the op.
 6. DEVICE ISOLATION VIA LISTS: device A's operation list never
    contains device B's operations and vice versa.
 7. ACCEPTED op -> Order PAID + Payment CASH/CAPTURED + op result
    links + stock decremented exactly once; REJECTED op -> no
    order/payment/sale ANYWHERE, stock untouched, tenant B zero rows.
 8. DUPLICATE + CONCURRENT SYNC regression within the correct scope.

 NOTE (verified, not changed): the guard chain (RBAC) runs BEFORE
 service tenant-scoping — an under-permissioned caller gets 403 before
 scoping hides the resource (the established Phase 2/3 convention). The
 full-surface replay therefore grants tenant B's admin the cross-domain
 READ keys (order:read, payment:read, inventory:read) so each probe
 reaches the tenant-scoping layer and proves the uniform 404 rather
 than stopping at RBAC. Documented in the spec.
