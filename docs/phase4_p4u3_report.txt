1. SCOPE
-----------------------------------------------------------------------
The resulting inventory scope is TENANT + STORE + VARIANT while the
tenant-global pool (storeId NULL) remains the default for every existing
non-POS flow. No parallel PosStock table; no second inventory engine; the
existing Inventory model/service/migration discipline carries the change.

Not implemented (later units): offline operation model (P4-U4), sync
protocol, offline payment boundary, reconciliation.

-----------------------------------------------------------------------
2. APPROVED D2 DECISION AS IMPLEMENTED
-----------------------------------------------------------------------
  - Inventory.storeId String? (nullable). NULL = tenant-global pool
    (the Phase 3 single pool, preserved verbatim). NOT NULL = a
    store-scoped pool.
  - Store-scoped uniqueness (storeId, variantId) — enforced as a PARTIAL
    unique index (Prisma DSL cannot express partial indexes):
      Inventory_storeId_variantId_key ON (storeId, variantId)
        WHERE (storeId IS NOT NULL)
  - The Phase 3 global uniqueness is preserved identically:
      Inventory_variantId_global_key ON (variantId)
        WHERE (storeId IS NULL)
  - All Phase 3 invariants preserved (see section 9).
  - FK: storeId -> Store, ON DELETE RESTRICT (stock blocks store
    deletion; P2003 -> 409, the PosDevice/PosSession precedent).

-----------------------------------------------------------------------
5. STORE RESOLUTION
-----------------------------------------------------------------------
  - INVENTORY API: store context is the PATH-PARAM store of the new
    endpoints (/inventory/stores/:storeId/...). The store is resolved
    through a tenant-scoped lookup: foreign/unknown store -> uniform 404
    'Store not found' (Asset.storeId precedent). Body storeId/tenantId is
    whitelist-rejected (400) — the store can never be injected.
    Check order: variant existence first (404 'Variant not found'),
    then store (404 'Store not found') — either message for a mixed
    foreign case proves no leak.
  - POS: the store is derived from the authenticated PosSession ->
    PosDevice -> Store chain (never the client); the sale passes it to
    OrderService as the INTERNAL inventoryScope option.
  - NON-POS flows: the global pool via the unchanged default.

-----------------------------------------------------------------------
6. INVENTORY API BEHAVIOR
-----------------------------------------------------------------------
Phase 3 routes (contracts unchanged — global pool):
  GET  /inventory/:variantId                 inventory:read
  POST /inventory/adjust                     inventory:manage

P4-U3 routes (store pools; same permissions):
  GET  /inventory/stores/:storeId/variants/:variantId   inventory:read
  POST /inventory/stores/:storeId/adjust                inventory:manage

Semantics per pool are identical: guarded atomic updateMany + increment,
quantityOnHand >= 0 DB CHECK, lazy row creation on first positive delta
with P2002 race retry, missing row == 0 on hand, BigInt-free integer
quantities. Two stores holding the same variant are fully independent
(partial unique indexes + scoped where-clauses).

-----------------------------------------------------------------------
7. ORDER INTEGRATION
-----------------------------------------------------------------------
  - CREATE (T1): createOrder gained an INTERNAL-ONLY options parameter
    (CreateOrderOptions.inventoryScope). Default 'global' — every existing
    caller and the public CreateOrderDto (untouched) behave exactly as in
    Phase 3. The POS orchestration passes the session's store. The
    guarded decrement's where-clause now includes the pool's storeId.
  - CANCEL (T3) RESTOCK — THE GAP CHECK: the unit instructions required
    stopping if existing Orders lacked trusted store information. The
    repository ALREADY records it deterministically: every POS order has
    a PosSale provenance row created in the same flow (UNIQUE(orderId))
    whose storeId is the pool T1 decremented. Cancel resolves the pool
    from that recorded data: POS order -> its PosSale store pool;
    non-POS order -> the global pool. No guessing, no Order schema
    change, no silent modification of Order semantics.
  - PROVEN: cancel of a Store A POS sale restores Store A exactly once
    (0 -> 2, never 4 or 5); Store B and the global pool untouched;
    repeated cancel -> 409 with no second stock write; a non-POS order
    restocks the global pool only.
