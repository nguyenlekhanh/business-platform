3. THE EXACT BOOKING MODEL
-----------------------------------------------------------------------
prisma/schema.prisma (all additive):
  enum BookingStatus {
    BOOKED
    CONFIRMED
    ACTIVE
    COMPLETED
    CANCELLED
    NO_SHOW
  }

  model Booking {
    id          String        @id @default(cuid())
    tenantId    String                    // server-derived (F5)
    serviceId   String                    // FK -> Service RESTRICT
    customerId  String?                   // FK -> Customer RESTRICT (nullable)
    startAt     DateTime                  // UTC, half-open [startAt, endAt)
    endAt       DateTime
    status      BookingStatus @default(BOOKED)
    createdAt   DateTime @default(now())
    updatedAt   DateTime @updatedAt

    tenant   Tenant   @relation(..., onDelete: Cascade)
    service  Service  @relation(..., onDelete: Restrict)
    customer Customer? @relation(..., onDelete: Restrict)

    @@index([tenantId])
    @@index([tenantId, createdAt, id])
    @@index([tenantId, serviceId, startAt, id])  // keyset for list
    @@index([serviceId])
    @@index([customerId])
  }

Field semantics:
- serviceId: FK to Service (tenant-scoped, must be ACTIVE). RESTRICT
  prevents deleting a Service with active bookings.
- customerId: optional FK to Customer (tenant-scoped). RESTRICT
  when present. Null = walk-in booking (Order precedent).
- startAt/endAt: UTC DateTime, half-open [startAt, endAt).
  CHECK(endAt > startAt) enforced at DB level.
- status: BOOKED default on create. PATCH carries lifecycle:
  BOOKED → CONFIRMED → ACTIVE → COMPLETED
  CANCELLED / NO_SHOW are terminals from any state.
  No delete endpoint; soft-retirement via CANCELLED/NO_SHOW.
  Future resource FK will RESTRICT deletion (Product/Category precedent).

4. TENANT ISOLATION

-----------------------------------------------------------------------
5. UNIQUENESS + CONCURRENCY (EXCLUDE CONSTRAINT)
-----------------------------------------------------------------------
No application-level read-then-create check. The DATABASE is the
final authority via a PostgreSQL EXCLUDE constraint using btree_gist
(already installed by migration 20260821020000):

  ALTER TABLE "Booking" ADD CONSTRAINT "Booking_no_overlap"
    EXCLUDE USING gist (
      "serviceId" WITH =,
      tstzrange("startAt" AT TIME ZONE 'UTC', "endAt" AT TIME ZONE 'UTC', '[)')
      WITH &&
    )
    WHERE ("status" IN ('BOOKED', 'CONFIRMED', 'ACTIVE'));

Semantics: two bookings for the SAME serviceId may not overlap in
time while either holds the slot. Half-open intervals [start,end)
mean back-to-back bookings (endA == startB) are legal. Status
predicate scopes the constraint to holding states; CANCELLED,
COMPLETED, NO_SHOW are excluded so historical bookings don't block
new ones.

Concurrency proven:
- Concurrent overlapping creation → DB UNIQUE arbitrates
  (exactly [201, 409], exactly one row).
- Overlap on update (rename time) → 409.
- Back-to-back intervals (endA == startB) → both 201.
- Different services at same time → both 201.
- Same service in different tenants → both 201.

All verified by integration tests (28/28).

7. API SURFACE
-----------------------------------------------------------------------
GET   /bookings             booking:read     200 { data, meta.nextCursor }
GET   /bookings/:id         booking:read     200 BookingSummary | 404
POST  /bookings              create|manage   201 BookingSummary | 409
PATCH /bookings/:id         booking:manage   200 BookingSummary | 404|409
- PATCH (not PUT) — Phase 3+ convention on new domains (D2).
- Guard chain: JWT (global) → TenantResolutionGuard → PermissionsGuard;
  TenantContextInterceptor; whitelist+transform+forbidNonWhitelisted.
- NO DELETE route — soft-retirement via PATCH status=CANCELLED/
  NO_SHOW. Future resource FK will RESTRICT deletion.
- NO staff/resource/schedule/availability/pricing/payment endpoints.

DTO Security:
CreateBookingDto: serviceId (cuid, required), customerId? (cuid),
startAt/endAt (ISO8601 UTC, required), status? (BookingStatus enum).
UpdateBookingDto: all-optional (empty patch = no-op).
BookingListQueryDto: PageQueryDto + status/serviceId/customerId filters.
Whitelist+forbidNonWhitelisted rejects all ownership fields
(tenantId/id/timestamps) AND deferred-domain fields (staffId,
resourceId, scheduleId, price, amountMinor, currency, durationMinutes)
with 400 — integration-proven with zero rows created.

-----------------------------------------------------------------------

  booking:read   → GET routes

imply manage); owner works without grants.
