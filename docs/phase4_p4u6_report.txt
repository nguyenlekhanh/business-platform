3. PAYMENT METHOD ENFORCEMENT (the implemented change)
-----------------------------------------------------------------------
Enforcement point: the SALE/PAYMENT-CREATION BOUNDARY, server-side â€”
not merely controller validation (per the unit instructions):
  - PosSaleService.createSale's INTERNAL options gained `offline?: boolean`.
  - When offline=true, any method other than CASH throws the
    deterministic ConflictException 'Offline payment must be cash'
    BEFORE any Prisma call (the earliest, safest point â€” nothing is
    read, created, or captured on rejection).
  - PosSyncService passes { allowClosedSession: true, offline: true } â€”

    Payment.
  - The ONLINE path is untouched: no option passed => no check runs.
    The online CARD flow (CreatePosSaleDto @IsIn(['CASH','CARD'])) is
    regression-proven unchanged.
  - Malicious-client analysis: the client cannot reach the boundary
    with a method at all â€” the intent DTO rejects 'method' (400), the
    sync route takes no body, and the boundary itself is internal-only.

5. IDEMPOTENCY (P4-U5 guarantees preserved and re-proven)
-----------------------------------------------------------------------
  - Retrying an ACCEPTED offline operation returns the SAME
    Order/Payment ids with NO second Payment, NO second Order, NO
    second capture, NO second inventory decrement (integration-proven:
    exactly one payment, still CAPTURED; stock decremented once).
  - Concurrent sync of the same operation: exactly ONE Payment, one
    Order, one inventory decrement, one capture; both callers receive
    the same durable result (real parallel HTTP + PostgreSQL; no sleeps,
    no memory locks â€” the DB claim arbitrates).
  - Rejected retry stays rejected deterministically (PRICE_CHANGED
    never becomes a payment).
  - No second payment-specific idempotency mechanism was created â€” the
    repository's existing mechanisms (T5 duplicate-CAPTURED guard, T2
    guarded capture, the P4-U5 processedAt claim) suffice.

-----------------------------------------------------------------------
6. FAILURE ATOMICITY (the existing transaction semantics, documented)
-----------------------------------------------------------------------
  - T1 (Order creation) is independently atomic: a failure rolls back
    its own order/items/stock writes.
  - T5 (payment create) is independently atomic and guarded (PENDING
    order + no prior CAPTURED).
  - T2 (capture) is independently atomic and guarded (both updates
    count==1 or abort).
  - The engine stages run in sequence T1 -> T5 -> T2; each failure
    leaves a consistent state, and validation runs BEFORE any of them
    so deterministic rejections mutate nothing. An engine
    'Insufficient stock' race after validation is caught by sync and
    persisted as OUT_OF_STOCK (deterministic).
  - Verified by direct DB row counts: no accepted operation without a
    valid Payment; no Payment without its Order; no duplicates; no
    inventory mutation without a successful sale.
