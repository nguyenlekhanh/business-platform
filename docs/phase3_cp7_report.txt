4. TEST COVERAGE (35 TESTS)
-----------------------------------------------------------------------

AUTHENTICATION / AUTHORIZATION (7 tests)
  - 401 for unauthenticated requests on all four endpoints:
    POST /payments, GET /payments/:id, POST /payments/:id/capture,
    POST /payments/:id/fail.
  - 403 for an authenticated user with no tenant membership.
  - 403 without payment:read (GET), payment:create (POST),
    payment:manage (capture and fail).
  - Manage-only role: can capture (200) but cannot read (403) or
    create (403).
  - Employee semantics: can create orders and payments but receives
    403 on payment read, capture, and fail.
  - Owner semantic-all: full payment lifecycle without explicit grants,
    including verification that the Order flips to PAID after capture.

TENANT ISOLATION / IDOR (5 tests)
  - Cross-tenant Payment GET returns the uniform 404 "Payment not
    found" while the same-tenant read of the same payment succeeds
    (no existence oracle).
  - Cross-tenant Order reference in POST /payments returns 404
    "Order not found".
  - Cross-tenant capture and cross-tenant fail both return 404 AND
    leave tenant B's Payment/Order rows untouched (verified directly
    in the database under tenant B's context).
  - Centralized tenant-scoping extension is proven active: the same
    prisma.payment.findUnique resolves inside tenant A's context and
    returns null inside tenant B's context.
  - Client-supplied tenantId in the create payload is rejected with 400
    by the whitelist (covered in the DTO-validation block).

DTO VALIDATION (2 tests)
  - Missing/empty orderId, missing/empty method, method exceeding
    MaxLength(50), non-string method -> 400.
  - Injection of tenantId, amountMinor, currency, status, id, createdAt,
    and unknown fields -> 400 (whitelist + forbidNonWhitelisted).

T5 — CREATE PAYMENT (2 invariant tests)
  - amountMinor equals the Order's subtotalMinor and currency equals the
    Order's currency; status is always PROCESSING; amountMinor is
    serialized as a JSON string (typeof 'string' asserted).
  - EUR fixture: a variant priced in EUR produces an EUR order and an
    EUR payment with the exact derived amount.

T5 — REJECTIONS AND DUPLICATE RULES (4 tests)
  - Unknown Order -> 404.
  - Foreign (tenant B) Order -> 404.
  - Non-PENDING (cancelled) Order -> 409 "Order is not pending".
  - Order with an existing CAPTURED payment -> 409 (either documented
    message — see section 8 note 2).
  - Multiple PROCESSING payments for one Order remain allowed (documented
    business rule): two payments created, both rows PROCESSING.

GET PAYMENT (3 tests)
  - Correct response shape with string BigInt amount.
  - Unknown payment -> 404.
  - Cross-tenant payment -> 404 while same-tenant access works.

T2 — CAPTURE (6 tests)
  - PROCESSING -> CAPTURED and Order PENDING -> PAID, verified both via
    the API and directly in the database (BigInt column intact:
    amountMinor = 2000n).
  - Transaction rollback: Order cancelled while the payment is
    PROCESSING, then capture -> 409 and the Payment update is rolled
    back (Payment remains PROCESSING; no partial CAPTURED/CANCELLED
    state ever exists).
  - FAILED payment cannot be captured (409, both rows unchanged).
  - Idempotent re-capture: second capture returns 200 CAPTURED with no
    further state changes.
  - Unknown payment capture -> 404.
  - Cross-tenant capture -> 404, tenant B state untouched.

T2 — FAIL (5 tests)
  - PROCESSING -> FAILED with the Order remaining PENDING (API + direct
    database row verification).
  - CAPTURED payment cannot be failed (409, both rows unchanged).
  - Idempotent re-fail: second fail returns 200 FAILED, no changes.
  - Unknown payment fail -> 404.
  - Cross-tenant fail -> 404, tenant B state untouched.

CONCURRENCY / ATOMICITY (3 tests, real — no mocks, no sleeps)
  - Two concurrent captures of the same PROCESSING payment: exactly one
    guarded updateMany wins; responses are only 200/409; final database
    state is CAPTURED payment + PAID order.
  - Concurrent capture vs fail on the same payment: deterministic
    [200, 409] outcome; final state is consistent (either
    CAPTURED+PAID or FAILED+PENDING — never both transitions applied).
  - Two concurrent payment creations for one PENDING order: both 201,
    two PROCESSING rows with distinct methods (documented T5 rule).

MONEY / SERIALIZATION
  - Every payment JSON response asserts amountMinor is a string.
  - Database rows assert the raw BigInt values remain exact.

8. BUSINESS INVARIANTS VERIFIED
-----------------------------------------------------------------------
  - Payment.amountMinor === Order.subtotalMinor (full-amount invariant).
  - Payment.currency === Order.currency (currency invariant).
  - Payment status is server-controlled and starts at PROCESSING.
  - T2 capture is atomic: Payment PROCESSING->CAPTURED and Order
    PENDING->PAID commit together or not at all; a failed guarded
    update rolls back the entire transaction.
  - T2 fail never modifies the Order (stays PENDING).
  - Terminal states are immutable: FAILED cannot capture, CAPTURED
    cannot fail; re-invocations are idempotent-success.
  - Concurrent transitions are arbitrated by guarded updateMany:
    exactly one winner, no corrupted intermediate states.
  - BigInt money is serialized as strings in every JSON response while
    the database retains exact BIGINT values.
