1. FINAL C1 CONTRACT — BOOKING → ORDER RELATIONSHIP
=======================================================================

1.1 REPOSITORY EVIDENCE
- Booking model (P5-U4): tenant-scoped, EXCLUDE on (serviceId, tstzrange)
  WHERE status IN ('BOOKED','CONFIRMED','ACTIVE')
- Order model (Phase 3 U6): tenant-scoped, T1 transaction (Order + OrderItems +
  Inventory decrement + Cart CONVERTED), immutable snapshots
- PosSale (P4-U2): additive provenance table, UNIQUE constraints on (orderId,
  paymentId), RESTRICT FKs, Order/Payment state machines untouched
- Customer: tenant-scoped, shared by Order/Reservation, nullable FK RESTRICT

1.2 EXACT RELATIONSHIP SPECIFICATION

| Property | Value |
|----------|-------|
| FK Direction | Booking.orderId → Order.id |
| Nullable | YES (optional) |
| Unique | NO (one Booking → one Order; one Order ← one Booking) |
| FK Direction | Booking.orderId → Order.id |
| ON DELETE | RESTRICT (P2003 → 409) |
| Can Order exist without Booking? | YES (walk-in orders, POS orders) |
| Can Booking exist without Order? | YES (always — optional link) |
| Can multiple Bookings reference one Order? | NO (1:1 provenance, like PosSale) |
| Tenant Invariant | Both tenant-scoped; link validated by tenantId |

1.3 SCHEMA CHANGES

ALTER TABLE "Booking" ADD COLUMN "orderId" TEXT NULL;

ALTER TABLE "Booking" ADD CONSTRAINT "Booking_orderId_fkey"
  FOREIGN KEY ("orderId") REFERENCES "Order"("id")
  ON DELETE RESTRICT ON UPDATE CASCADE;

CREATE INDEX "Booking_tenantId_orderId_idx" ON "Booking"("tenantId", "orderId");

1.4 TENANT INVARIANT
- Both Booking and Order are in TENANT_SCOPED_MODELS
- Prisma extension merges tenantId into every top-level operation
- Cross-tenant reference → uniform 404 (no existence oracle)
- Link creation validates tenantId match via extension

1.5 ORDER WITHOUT BOOKING
- YES — walk-in orders, POS orders, cart checkout without Booking
- Order.bookingId is NOT added (reverse link not needed)
- Order remains the commerce root; Booking is optional provenance

1.5 BOOKING VALID STATES FOR LINKING
- Only BOOKED, CONFIRMED, ACTIVE bookings can be linked
- CANCELLED, COMPLETED, NO_SHOW → 409 Conflict
- Booking.status validated at link time

1.6 ALREADY-LINKED BOOKING
- Attempt to link already-linked Booking → 409 Conflict
- Error: "Booking already linked to an Order"

2. FINAL C2 WORKFLOW — LATER CHECKOUT
=======================================================================

2.1 WORKFLOW SEQUENCE

```
1. Customer/Staff creates Booking (POST /bookings)
   → Booking created with status BOOKED, no Order link
   ↓
2. Later: Customer arrives / POS checkout
   ↓
3. POST /bookings/:id/checkout
   → Validate Booking exists, tenant matches, status ∈ {BOOKED,CONFIRMED,ACTIVE}
   → Check existing orderId (if already linked → return existing Order 200)
   → Create Order via existing T1 (OrderService.createOrder)
   → Link Booking.orderId = Order.id (conditional UPDATE WHERE orderId IS NULL)
   → Return Order + linked Booking
```

2.2 EXACT HTTP CONTRACT

POST /bookings/:id/checkout
Headers: Authorization: Bearer <jwt>, X-Tenant-ID: <tenantId>
Body: { items?: [], customerId?: string }  // Optional: override/add items/customer
Response: 200 { order: OrderSummary, booking: BookingSummary }

Headers: booking:manage + order:create

2.3 EXISTING ENDPOINT REUSE

- Order created via OrderService.createOrder (existing T1)
- Reuses: uniform currency validation, guarded stock decrement, snapshots
- No new Order creation logic — reuses OrderService.createOrder
- Booking only provides: serviceId, customerId, startAt, endAt as input hints

2.4 EXISTING POS INTEGRATION

- POST /pos/sales already creates Order + Payment + PosSale (P4-U2)

3. FINAL C8 CONTRACT — IDEMPOTENCY CONTRACT
=======================================================================

3.1 REPOSITORY EVIDENCE

- Booking creation: idempotent via EXCLUDE (serviceId, startAt)
  Concurrent duplicate → [201, 409], exactly one row
- Order creation (T1): NOT naturally idempotent (no natural key)
  T5 allows multiple PROCESSING payments
- PosOperation (P4-U4): idempotency via (deviceId, clientUuid) UNIQUE
- PosSale: UNIQUE constraints on orderId, paymentId (1:1)

3.2 C8 DECISION: NATURAL KEY (BookingId)

The checkout operation is idempotent via BookingId:

```
POST /bookings/:id/checkout
→ Check Booking exists, tenant matches
→ If Booking.orderId exists → return existing Order (200)
→ Else: create Order (T1) + conditional UPDATE Booking SET orderId = $1
     WHERE id = $1 AND orderId IS NULL
```

3.3 CONCURRENT CHECKOUT REQUESTS

Request A: checkout Booking X
Request B: checkout Booking X (simultaneous)

Database guarantees:
1. First UPDATE wins (conditional UPDATE WHERE orderId IS NULL)
2. Second UPDATE affects 0 rows → detects conflict
3. Re-read Booking → orderId now set → return existing Order (200)

This uses existing Prisma primitives — no new locking framework.

3.4 RETRY SCENARIO

Request 1: checkout Booking X → create Order + link → network fails before response
Request 2: retry checkout Booking X → finds orderId set → returns existing Order (200)

No duplicate Order created. Booking already linked.

3.5 RETRY AFTER ORDER CREATION FAILURE

If Order creation fails (e.g., insufficient stock):
- Booking remains unlinked (orderId NULL)
- Retry safe: Booking still unlinked, checkout can retry
- No partial state persisted

3.6 RETRY AFTER PARTIAL SUCCESS

If Order created but link UPDATE fails (race condition):
- Order exists, Booking unlinked
- Retry: UPDATE succeeds on second attempt
- Or: GET /bookings/:id/checkout sees existing orderId → returns Order

No orphan Orders created (Order exists but unlinked — acceptable,
cleanup via admin or future reconciliation).

6. TRANSACTION BOUNDARY
=======================================================================

6.1 SINGLE TRANSACTION REQUIRED

The checkout operation (create Order + link Booking) MUST execute in
a single Prisma interactive transaction ($transaction).

WHY:
- Atomicity: Order created + Booking linked, or neither
- Consistency: no orphan Order (created but unlinked), no orphan link
- Concurrency: conditional UPDATE prevents duplicate link
- Rollback: if Order creation fails, Booking remains unlinked

6.2 EXISTING PATTERN REUSE

Reuses OrderService.createOrder (existing T1 transaction) +
conditional Booking UPDATE in same $transaction.

Pattern from PosSaleService.createSale:
- Uses OrderService.createOrder inside $transaction
- Then creates Payment, PosSale in same tx

Our pattern:
```typescript
return this.prisma.$transaction(async (tx) => {
  // 1. Create Order via existing T1 (via OrderService, adapted for tx)
  const order = await this.createOrderInTx(tx, userId, checkoutData);

  // 2. Link Booking (conditional update)
  const updated = await tx.booking.update({
    where: { id: bookingId, orderId: null },  // conditional!
    data: { orderId: order.id },
  });
  if (!updated) throw new ConflictException('Booking already linked');

  return { order: this.toOrderSummary(order), booking: this.toBookingSummary(updated) };
});
```

6.3 NO OUTBOX/EVENT MECHANISM

Synchronous $transaction sufficient. No outbox, no event bus, no
async compensation. Repository pattern: synchronous T1 for Order.

7. CONCURRENCY GUARANTEES
=======================================================================

7.1 BOOKING CREATION
- EXCLUDE (serviceId, tstzrange) WHERE status IN ('BOOKED','CONFIRMED','ACTIVE')
- Concurrent duplicate → DB UNIQUE arbitrates [201, 409], exactly one row

7.2 ORDER CREATION (T1)
- Guarded updateMany on Inventory (quantityOnHand >= qty)
- Multiple PROCESSING payments allowed (T5)
- Guarded updateMany on Payment/Order (T2)

7.3 CHECKOUT CONCURRENCY

Request A: checkout Booking X
Request B: checkout Booking X (simultaneous)

Guarantee: Conditional UPDATE (WHERE orderId IS NULL)
- First UPDATE wins (1 row affected)
- Second UPDATE affects 0 rows → detected
- Re-read Booking → orderId set → return existing Order (200)

No lost update, no double Order, deterministic 409/200.

7.4 CROSS-DOMAIN CONCURRENCY

Booking EXCLUDE (serviceId, time) — temporal concurrency
Order T1 (Inventory) — stock concurrency
Independent domains, independent guards.

No new locking, no application-level locks, DB is authority.
