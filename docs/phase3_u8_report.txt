2. CUSTOMER DELETION WITH ORDERS (REQUIREMENT A)
-----------------------------------------------------------------------
Production branch verified: src/customer/customer.service.ts:186-203.
The delete path catches Prisma P2003 (FK RESTRICT violation) and maps:
  - error message containing 'Order'    -> 409
    "Customer has orders and cannot be deleted"
  - otherwise (Reservation FK)          -> 409
    "Customer has reservations and cannot be deleted"

Test results (all in the U8 suite):
  - Customer with NO orders keeps the documented delete behavior:
    DELETE /customers/:id -> 204 No Content; row verified gone via
    direct Prisma.
  - Customer WITH an existing Order CANNOT be deleted:
    DELETE -> 409 "Customer has orders and cannot be deleted".
    No partial deletion: Customer row remains, Order row remains,
    Order.customerId still references the customer, Order stays
    PENDING, and the order remains fully queryable through the API
    afterwards.
  - Customer with reservations keeps the documented reservation
    message (409 "Customer has reservations and cannot be deleted").
  - Cross-tenant deletion attempt returns the uniform 404
    "Customer not found" (no existence oracle) and leaves the owning
    tenant's customer untouched.

  1. Category creation   -> row verified (tenantId ownership).
  2. Product creation    -> row verified, categoryId + tenantId link.
  3. Variant creation    -> row verified, productId + tenantId link.
  4. Price upsert (PUT)  -> row verified: amountMinor exact BIGINT,
                            one current price per (variant, currency).
  5. Inventory adjust    -> row verified: quantityOnHand = initial.
  6. Cart + items        -> two adds MERGE by (cartId, variantId):
                            quantity 2 + 3 = 5; live totals
                            [{ currency USD, totalMinor "6250" }].
  7. Order from cart checkout (empty body):
                            status PENDING; subtotalMinor "6250"
                            (5 x 1250, exact BigInt math); cart row
                            verified CONVERTED; stock verified
                            30 -> 25 (guarded decrement-on-order);
                            OrderItem snapshot verified: unitAmount
                            1250n, lineTotal 6250n, sku frozen at
                            order time.
  8. Payment creation    -> PROCESSING; amountMinor "6250" and
                            currency "USD" DERIVED FROM THE ORDER
                            (server-side; client supplies only
                            orderId + method); amountMinor is a JSON
                            string at the API boundary while the DB
                            column holds exact BIGINT 6250n.
  9. Capture             -> 200; Payment CAPTURED.
 10. Final state         -> direct DB rows: Payment.status CAPTURED,
                            Order.status PAID; API GET order returns
                            PAID. Post-capture invariants: cancelling
                            a PAID order -> 409; creating a second
                            payment for the PAID order -> 409; failing

5. SECURITY (REQUIREMENT D)
-----------------------------------------------------------------------
Cross-tenant isolation / IDOR:
  From tenant B (full-grant admin), every probe into tenant A's data
  fails with the uniform 404 (no existence oracle): GET inventory,
  add cart item (foreign variant), create order (foreign variant and
  foreign customerId), GET order, cancel order, GET payment, capture
  payment, fail payment, create payment for a foreign order, delete a
  foreign customer. Tenant A's catalog, stock, order, and payment
  rows were verified fully intact afterwards (order PENDING, payment
  PROCESSING, stock decremented only by tenant A's own order).

Server-derived tenantId:
  Injecting tenantId into payloads (categories, cart items, orders,
  payments) is rejected with 400 by the DTO whitelist; no rows leaked
  into tenant B (verified: 0 payment rows there).

RBAC / ownership:
  Owner semantic-all walks the entire cross-domain flow (catalog ->
  cart -> order -> payment -> capture -> PAID; stock 8 -> 6) with no
  explicit grants.

Tenant-scoped Prisma models remain scoped; all row verifications run
inside tenantContext.run(async () => ...) so the centralized extension
is the enforcer being exercised. No raw SQL is used anywhere in the U8
spec or introduced into production.
